---
title: "The login that only failed after it worked"
description: "Putting single sign-on in front of the homelab, and the failure that survived every check I had, because an authorization redirect looks identical whether or not the token exchange behind it agrees."
date: 2026-09-03
---

Until this month every service in the house had its own login, which meant every service had its own way of being slightly wrong. So I put an identity provider in front of the lot, and it does two quite different jobs at once. For the services that are only ever opened in a browser it sits at the ingress as a gate: the reverse proxy asks it about a request before forwarding anything, and an unauthenticated visitor gets bounced to a portal and never reaches the application at all. For everything else it is an OpenID Connect provider, and the application itself does the redirecting, because those applications have clients that a gate at the front door would break. Six of them log in against it that way now. Two mechanisms for one job sounds like indecision, and it is not; the split is forced, and working out where the line falls was most of the design.

The line falls on whether anything but a browser talks to the thing. A gate at the ingress is indiscriminate, which is exactly what makes it good: it does not know or care what is behind it. That is fine for a wiki and a dashboard. It is fatal for the photo library and the file server and the git host, because those are reached by a phone app, by a file-sync client speaking WebDAV, by git over HTTPS, and by a document scanner hitting an API path. None of those can follow a redirect to a login portal. Put the gate in front of them and they do not fail loudly, they fail as a sync client that has quietly stopped syncing. So those services get OIDC instead, where the application understands the protocol and can keep its own token and app-password paths working alongside it.

The gate needed two middlewares chained in a fixed order, and the order is not decorative. Traffic from the internet arrives at the proxy as plain HTTP, because the tunnel terminates TLS out at the edge and carries the request the rest of the way unencrypted. The identity provider refuses to protect a target it believes is plain HTTP, and rightly so, so it rejects the request outright before authentication is ever considered. The first middleware exists solely to tell it the original scheme was HTTPS, and it has to run before the one that does the actual check. Miss that and you get the most misleading result available: it works perfectly on the LAN, where the request really did arrive over HTTPS, and fails only from the internet. I then made the same mistake a second time, because the portal's own hostname is served through the same proxy and needs the same treatment, which is not obvious when you are thinking of it as the thing doing the protecting rather than as one more protected host.

The one deliberate hole is that the internal names stay ungated. Every service still answers unauthenticated on the house network, and that is not laziness, it is the recovery path. The identity provider is a single point of failure sitting in front of the tools I would need to repair it, and a locked-out administrator with no way back in is a worse outcome than a LAN-only bypass in a house I control. The deployment tool keeps its own local login for the same reason, since it is the thing that repairs the identity provider when the identity provider is what broke. I would not accept either of those trades at work, where the network is not a trust boundary and the blast radius is other people. Here the honest framing is that the LAN is the break-glass, and writing that down as a decision is better than discovering it as an accident.

Two failures are worth keeping. One is that a login can succeed and then die immediately afterwards for a reason that has nothing to do with authentication: the hypervisor's own interface sets large cookies, and once its own session was established the request carrying all of them exceeded the proxy's default header buffer, so the browser got a size error the moment the login was over. Nothing in that error mentions authentication, and everything about the timing points at it. The other is the one I will actually carry forward. An OIDC flow has two legs, and only the first is visible: the browser gets redirected, comes back with a code, and lands on a logged-in page. Behind that, the application swaps the code for a token over a channel you never see, and the two ends have to agree on details that live in separate files. One application and I disagreed about how it should present its credentials on that second leg. The redirect looked perfect. Every check I had short of a human sitting down and logging in passed. It surfaced only when someone actually logged in. So the rule I am writing down is that an authorization redirect proves nothing about the token exchange, and a client is not wired until a person has been all the way through it, which is why two of the six are still marked unverified rather than done.

The work also cost me a premise I had been carrying for months. I had assumed a public hostname with no route configured for it was therefore internal, and had been treating that as a security property. It is not one: the tunnel carries a wildcard, so every name under the domain is reachable from the internet unless something explicitly pins it to the internal entrypoint. Two services I had filed as LAN-only were nothing of the sort. That is a much better thing to learn while adding authentication than at any other time, but it is a reminder that the most dangerous item in a threat model is the one you believe you have already handled.
